# LM0 V3 source specification

V3 is an opt-in source language in LM0 0.6. Start with `module NAME version 3`.
The native C frontend lowers it to the typed core and assembly backend.
V1/V2 source and existing C scalar/pointer and library ABIs remain supported.
Use [the generation contract](llm.md) for short working instructions.

## Syntax and names

Newlines end statements. Bodies follow `:` and use consistent space indentation;
blank/comment-only lines do not affect indentation. A body must contain a
statement (`pass` is allowed). Multiline expressions, semicolon-separated
statements, tuples, comprehensions, closures, exceptions and methods are absent.
Identifiers are ASCII; the `__lm0_` prefix belongs to the compiler.
Intrinsic names such as `len`, `view` and `cast` are reserved as function names.

```text
module example version 3
use std_vec
data message = "hello\n"
struct Node:
    value:i64
    next:ptr<Node>

fn sum(values:slice<i64>) -> i64:
    result = 0
    for value in values:
        result += value
    return result
```

Declarations are `use MODULE`, `data NAME = JSON_STRING`, indentation-delimited
`struct`, and explicitly typed functions. `extern c fn name(...) -> T` has no
body; `export c fn name(...) -> T:` exports a definition. Names have no sigils.
Calls may reference later declarations, including recursion.

Statements are assignment (`=`, `+=`, `-=`, `*=`), void expression statements,
`return [expression]`, `pass`, `if`/`elif`/`else`, `while`, `for`, `break`, and
`continue`. Assignment targets are names or indexed elements. Every non-void
expression statement must instead assign its result. A non-void function must
return on every statically reachable path; loops are conservatively allowed to
execute zero times. Statements after a terminating statement are errors.

## Types, expressions and evaluation order

Function parameters and returns remain explicit. Existing scalar, pointer,
fixed-array and struct types retain their core meanings; arrays/structs are
memory objects. Locals infer their type from their first assignment. An optional
annotation, `count:u64 = 0`, selects the type. Reassignment retains it. Parameter
reassignment changes the local binding. There is one local namespace per
function; branches do not introduce shadowing scopes. Definite assignment takes
the intersection of reachable branches. A loop-body assignment alone does not
make a name available after the loop.

Numeric literals use established operand/interface types, or default to i64/f64.
An explicit literal annotation such as `1:u32` must agree with its use.
`true`/`false` are bool. Null needs a pointer context or annotation. There are no
implicit casts. Numeric conversions use `cast<T>(value)`.

Precedence, highest first: postfix calls/indexing and parentheses; unary `-`/`~`;
`* / // %`; `+ -`; `<< >>`; `&`; `^`; `|`; comparisons `== != < <= > >=`;
`not`; `and`; `or`. Binary operators associate left. Comparisons do not chain:
write `a < b and b < c`. Conditions and `and`/`or` operands are strictly bool;
Boolean operators return bool and short-circuit.

Expressions and call arguments evaluate left to right. Indexed assignment
evaluates the target address/index before the right-hand expression. Compound
assignment reads the target once before evaluating its right-hand side.

Integer operations retain V2 wrapping and traps. Both `/` and `//` use the core
division operation: integer division truncates toward zero, not Python's floor
division. Remainder has the dividend's sign. Floats retain the IEEE behavior
specified in [spec.md](spec.md). Boolean/numeric casts remain forbidden.

## Sequences and control flow

`slice<T>` is a borrowed pointer/length pair for scalar T. Construct a view with
`view(pointer, length:u64)`. Lengths must fit i64; `len(slice)` returns i64.
Index reads and writes require i64 indices and trap outside `[0, len)`.
Negative indexing and subslicing are absent. Assignment aliases storage; it
does not copy, retain, destroy or extend its lifetime. Raw-pointer operations
still require valid bounds, initialization and lifetimes.

`for value in slice` captures the view and length once, reads each element when
visited, and assigns it to the loop variable. Updating an element does not update
the already-read variable. `range(stop)`, `range(start, stop)`, and
`range(start, stop, step)` evaluate i64 bounds once, exclude stop, and require a
positive step (otherwise trap). A mathematical next value beyond i64 maximum
ends iteration instead of wrapping. `break`/`continue` affect the nearest loop.

Slice parameters flatten to pointer then u64 length, in parameter order, for
native calls and V3 C exports/imports. For example,
`solve(data:slice<i64>, key:i64) -> i64` has C ABI
`int64_t solve(int64_t *data, uint64_t length, int64_t key)`.
Slice returns and slices nested inside storage types are unsupported. Existing
scalar/pointer signatures are unchanged. Executables use `fn main() -> i32`.

## Core and library operations

| V3 expression/statement | Core operation |
| --- | --- |
| `load(p)`, `store(p, x)` | Exact element-type access |
| `stack<T>(N)` | Constant-size storage hoisted to entry |
| `alloc<T>(count)`, `free(p)` | Explicit heap allocation/destruction |
| `offset(p, index)`, `field(p, name)` | Raw element/field address |
| `copy(dst, src, bytes)`, `move(dst, src, bytes)` | Disjoint/overlap-safe copy |
| `address(name)` | Static bytes, without implicit NUL |
| `sizeof<T>()`, `alignof<T>()` | Storage layout as u64 |
| `cast<T>(x)`, `ptrtoint(p)`, `inttoptr<T>(x)` | Explicit conversions |
| `trap()` | Process-terminating trap |

Count/byte operands retain u64 types and offsets retain i64. Repeated execution
of a syntactic `stack` expression refers to the same entry allocation. Heap and
library resources remain manually managed; there is no garbage collector or
automatic status propagation.

`library describe MODULE FUNCTION... --syntax v3` returns V3 signatures and call
templates. Its default remains V2. V3 compact inspection automatically uses V3
library templates. Signatures, contracts and ABI identity derive from
`stdlib/catalog.json`; generated files are not edited.

## Inspection, repair and implementation limits

`inspect --function NAME --view compact` returns original source/signatures,
referenced contracts, validation, unresolved dependencies and the source hash.
Generated blocks are not replacement units. Parseable invalid functions remain
inspectable; the first validation error is retained even when lowering cannot
produce a valid body. `replace` accepts one complete function, checks the expected
revision and validates the whole module before writing atomically. V3 `--block`
and V3-to-V2 `migrate` are rejected; V1-to-V2 migration is unchanged.

The frontend lowers locals and intermediates through stack slots and carries slot
addresses through generated block interfaces. This prioritizes correctness at
`-O0`; smaller source is not a runtime optimization claim. Spans and hashes refer
to input V3 text. `limits.type_depth` bounds nesting/indentation;
`limits.v3_source_expansion` (default 64) bounds generated text relative to
`limits.source_bytes`.
